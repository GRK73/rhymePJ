# 프로젝트 전체 검토 — 2026-09-22

후속 수정과 현재 상태는 [검토 후 수정 내역](project_fixes_20260922.md)을 참고한다. 아래 내용은 수정 전 발견 사항이다.

## 결론

연결 검색의 인덱스·캐시·주제 재채점과 프리로딩은 현재 검사에서 동작했다. 단어 검색도 실제 정적 자산으로 실행됐다. 다만 오류 복구, 연결 발음 모드, 단어 검색 제외어 처리에 수정할 문제가 있으며, GitHub Pages 배포 준비는 완료되지 않았다.

이번 검토는 현재 작업 폴더의 미커밋 변경을 포함한다. GitHub의 배포된 사이트를 검사한 결과가 아니다. 제품 코드는 수정하지 않았고, 검토 문서와 재현·검사 산출물을 남겼다. 신규 주제 모델 비교는 사용자의 보류 요청에 따라 실행하지 않았다.

## 확인된 문제

### 1. [P1] 단어 검색 Worker 오류 후 재검색이 끝나지 않을 수 있음

- 위치: `public/js/v2/search-runtime.js:37`, `:98`.
- 초기화가 성공한 뒤 Worker 오류가 발생하면 오류 처리기는 대기 요청만 거절한다. 기존 `worker`, 완료된 `initPromise`, `workerStatus`를 정리하지 않는다.
- 다음 검색은 기존 초기화 Promise를 재사용하고 같은 Worker에 요청한다. Worker가 더 이상 응답하지 않으면 요청이 남으며 별도 timeout도 없다. 검색 화면은 계속 기다리게 된다.
- 가짜 Worker로 초기화 성공 → 오류 → 재검색을 재현했다. 생성 Worker 수는 1이고, 재검색 요청 1개가 pending에 남았다. 이 검사는 브라우저가 실제로 충돌했다는 뜻이 아니라 충돌 시 복구 경로가 없다는 재현이다.
- 조치: 오류 시 Worker 종료·참조 및 초기화 상태 초기화, 요청 timeout, 다음 검색에서 Worker 재생성. 연결 검색의 복구 정책을 참고하고 단어 검색에도 회귀 검사를 추가한다.

### 2. [P1·배포 준비] 현재 Pages workflow만으로 배포를 완성할 수 없음

- 위치: `.github/workflows/deploy.yml:25`, `:40`; `scripts/stage_pages_artifact.js:89`.
- 실제 `public/data/deployment-allowlist.json`이 없다. `node scripts/stage_pages_artifact.js`는 허용 목록 누락으로 종료됐다. README에도 이미 기재된 미완료 사항이며, 검토 과정에서 새로 생긴 회귀가 아니다.
- 생성된 단어 검색·연결 검색·연결 인덱스 자산은 Git에서 제외되지만 workflow에는 이를 생성하거나 검증된 artifact에서 가져오는 단계가 없다. 로컬에 존재한다는 사실만으로 Actions에 공급되지는 않는다.
- `npm test`는 Python 테스트를 호출하지만 workflow는 Node 의존성만 설치한다. Python 버전과 `.[build,test]` 의존성을 설치하는 단계도 필요하다. 현재 로컬 대체 Python에서는 `pyarrow` 누락으로 4개 테스트 모듈을 가져오지 못했다. Actions 자체를 이번에 실행한 것은 아니다.
- 조치: 자산 공급 → 무결성 검증 → 허용 목록에 따른 staging → 실제 artifact UI 검사 순으로 배포 경로를 완성한다. 연결 검색의 새 gzip/index 파일도 목록에 포함해야 한다. 허용 목록의 검토 상태를 형식적으로 바꿔 검사를 우회하면 안 된다.
- 정정: 처음 일반 권한 검사에서는 단어 검색 manifest가 없는 것으로 표시됐으나, 읽기 권한을 확보한 재검사에서 파일과 attestation이 모두 확인됐다. 실제 정적 자산 66개, 69,756,809바이트는 release 검사를 통과했다. 로컬 단어 검색 데이터 누락은 문제 목록에서 제외한다.

### 3. [P2] 연결 검색의 발음 모드가 점수 계산에 반영되지 않음

- 위치: `public/js/app.js:170`; `public/workers/linked-worker.js:42`, `:63`; `public/js/linkedRhyme.js:9`.
- UI는 연결 검색에서 원어·한국어식·혼합 모드를 선택하게 한다. Worker는 `pronunciationMode`를 검증하고 캐시 키에 넣지만, 분할 생성과 후보 발음·점수 계산에는 전달하지 않는다.
- 실제 데이터와 production Worker 코드를 사용해 영어 결과를 검색했다. `time`은 세 모드 모두 874개, `타임`은 모두 249개였으며, 각 검색어의 전체 결과 JSON 해시도 세 모드가 같았다.
- 모드를 바꾸면 동일 계산을 다시 수행하면서 후보 캐시만 무효화한다.
- 조치: 모드별 query/candidate 발음 경로와 해당 인덱스를 연결한다. 지원 전까지는 옵션을 비활성화하고 적용 범위를 명시한다. 기존 인덱스가 원래 발음으로 생성됐으므로 요청 인자만 전달하는 수정으로 끝내면 안 된다.

### 4. [P2] 단어 검색 제외어가 Top-50 제한 뒤에 적용됨

- 위치: `public/js/v2/search-ui-adapter.js:46`, `:80`; `public/js/v2/search-core.js:625`.
- Worker는 상위 50개만 반환하고, UI가 그 결과에 제외어를 적용한다. 제외된 자리를 조건에 맞는 하위 후보로 채우지 않는다.
- 예를 들어 상위 50개가 제외 대상이고 51위가 유효하면 화면은 결과 없음으로 표시된다. 순위 fixture와 실제 UI adapter를 사용해 제한 전 유효 후보 1개 → 현 처리 순서에서는 0개를 재현했다. 실데이터에서 특정 검색어가 이 극단적 상태라는 주장은 아니다.
- 조치: 제외어를 Worker 요청 계약에 포함하고 결과 개수 제한 전에 적용한다. 후보 수 제한으로 인한 누락까지 줄이려면 후보 선택 단계의 제외 처리도 함께 설계한다.

## 성능·품질에서 남은 개선 여지

### 단어 검색 첫 로딩

`public/js/v2/static-search-loader.js:198`은 초기화에서 모든 발음 레코드를 읽는다. 현재 manifest에는 230,713개 발음이 45,287,018바이트 JSON 한 파일로 들어 있다. 이는 압축 전 자산 크기이며 GitHub Pages의 실제 전송량을 측정한 값은 아니다.

언어 또는 레코드 조각별 선택 로딩과 압축·바이너리 포맷을 검토할 가치가 크다. 먼저 작은 query lookup으로 발음을 찾고, posting이 가리키는 레코드만 읽도록 변경하면 첫 준비 부담을 줄일 수 있다. 단순히 파일을 여러 개로 나누고 모두 읽으면 이 목적을 달성하지 못한다. 기존 정적 검색 parity 검증을 유지해야 한다.

단어 검색 UI의 시간·로드량은 초기화 이후의 search diagnostics 중심이다. 이번 Chrome 검사에서 기본 검색 wall time은 약 1.73초였지만 상태 표시 시간은 590ms였다. 둘은 측정 범위가 다르다. 최적화 비교에서는 초기화 포함 첫 검색과 warm 검색을 분리해야 한다. 이번 단일 실행 수치는 전후 개선율의 근거가 아니다.

### 연결 검색 후보의 범위

`public/js/search/linked-candidates.js:16`은 앞 단어 후보를 200개로 제한한다. 영어는 앞끝 점수를 기준으로 이 후보를 고른 다음 뒤 단어와 주제를 평가한다. 한국어 표면 검색에서는 정확히 일치하는 앞 후보를 유지하고, 발음 fallback 후보를 200개로 제한한다.

현재 캐시는 이 탐색 범위에서 생성된 후보 전체를 보존하므로 재채점의 정확성을 지킨다. 하지만 처음부터 제외된 앞 후보까지 복구하지는 않는다. 따라서 주제에 가장 적합한 전체 사전의 조합을 보장하는 구조는 아니다. 향후 후보 확장 또는 점수 상한 기반 탐색을 검토하되, 현재 속도와 결과를 기준으로 recall을 측정해야 한다. 기존 제한을 유지한 것이므로 이번 캐시 최적화의 회귀로 분류하지 않는다.

### 주제 검색 지원 범위

한국어 → 영어 주제는 107개 수동 매핑과 기존 50차원 벡터를 사용한다. 임의의 한국어 주제를 이해하는 다국어 모델이 아니다. 매핑이 없으면 해당 언어의 주제 보정을 생략하고, 후보 벡터가 없으면 중립 점수로 후보를 유지한다. 이미 문서화된 의도된 정책이다. 모델 교체 검토는 추후 비교 단계에서 진행한다.

### 오래된 비교 명령

`scripts/search/check_loading_modes.mjs:67`은 현재 결과가 opt2 기준선과 완전히 같아야 한다고 검사한다. 이후 적용된 한국어 → 영어 주제 연결·벡터 없는 후보 유지와는 기대 계약이 다르다. 해당 전체 명령은 이번에 실행하지 않았다. 주제 변경을 허용하는 검사와 무손실 로딩 회귀 검사를 분리하고, README의 비교 명령도 현재 기준에 맞춰 정리할 필요가 있다.
