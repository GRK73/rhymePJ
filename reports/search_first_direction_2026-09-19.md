# 검색 중심 전환 제안 — 2026-09-19

이번 사용자의 방향 변경을 기준으로 작성한 조사 결과다. 기존 V2 생성·가사 분석 로드맵을 앞으로의 제품 목표로 사용하지 않는다. 이 문서는 설계 제안이며, 앱 기능 제거 또는 새 검색 엔진의 구현 완료를 뜻하지 않는다.

## 1. 확정 범위와 권장 결론

- 가사 생성과 가사 세부 분석은 제품 범위에서 제외한다.
- 한국어·영어 단어 라임과 두 어절/두 단어 연결 라임을 첫 범위로 한다.
- 기존 한영 교차 단어 검색 및 다른 언어의 입력으로 단일 언어 연결 결과를 찾는 기능도 회귀 범위에 포함한다.
- 한 연결 구문 안의 한영 혼합과 3어절 이상은 후속 확장으로 둔다.
- 우선순위는 검색 속도, 그다음 검색 품질 유지·향상이다.
- 운영은 GitHub Pages 정적 파일만으로 완결한다. Python·SQLite·형태소 분석·학습은 개발/빌드 도구로만 사용할 수 있다.

**권장 방향: 현재 발음 자산과 점수식을 재사용하되, 단어·연결 검색 모두 빌드 시 생성한 음소 경계 인덱스를 Web Worker에서 조회한다.** 처음에는 점수식을 고정한 최적화를 하고, 검증 후 발음·자연스러움 개선을 분리 적용한다. 브라우저 생성 모델 도입은 이 목표의 우선 작업이 아니다.

## 2. 코드에서 확인한 병목

### 연결 라임

`public/js/app.js`의 `appendSurfaceLinkedResults()`는 검색어 분할마다 `Object.entries(surfaceEntries)` 전체를 돈다. 표기 일치가 없는 많은 어절에서 발음 후보 생성과 `getBestBoundaryScore()`를 호출한다. 결과적으로 가장 비싼 발음 검사를 후보 추출 전에 수행한다.

영어 경로도 분할마다 `dictByLang` 전체를 채점하고 앞 단어 상위 200개를 고른 다음 그 단어의 follower를 조회한다. 이는 느릴 뿐 아니라 왼쪽 점수가 조금 낮아도 오른쪽 발음·결합 자연스러움이 좋은 쌍을 미리 탈락시킬 수 있다. 한국어 fallback에도 앞 후보 200개 제한이 있다.

추가 비용과 품질 제약:

- 연결 검색의 계산 루프는 메인 스레드에서 동기 실행한다. Worker 이동은 화면 멈춤을 줄이지만 자체적으로 연산량을 줄이지는 않는다.
- 검색마다 언어별 사전 필터링과 단어 Map을 다시 구성한다.
- 보조 사전 31.61MiB, 한국어 surface bigram 36.42MiB, 구어 surface bigram 32.61MiB 등이 별도 JSON이다. 이는 압축 전 파일 크기이며 실제 네트워크 전송량이 아니다.
- 주제를 켜면 기존 한영 벡터 JSON 총 약 94.70MiB를 읽는 경로가 있다.
- 보조 코퍼스 점수를 구할 때 follower 목록에서 `.find()`를 반복한다. 빌드 시 pair record로 합칠 수 있다.
- `scripts/build_surface_bigram_index.py`는 head당 기본 상위 30 follower만 저장한다. 인덱스를 빠르게 만들어도 원본에서 잘려 나간 좋은 연결은 복원되지 않는다.
- `scripts/validate_linked_search_pipeline.js`는 이미 suffix index를 사용하지만, 제품의 전체 연결 검색 함수를 그대로 실행하지 않는다. 따라서 기존 60건 통과를 앱 전체 순위·속도 검증으로 간주할 수 없다.

### V2 단어 검색

현재 Worker 기반은 재사용할 가치가 크지만 다음 비용이 남아 있다.

- 발음 record 약 43.19MiB를 초기화 시 전부 읽고 JSON으로 파싱한다. 그 외 posting을 질의별로 추가 로딩한다.
- 넓은 posting에서 10만 개 이상의 후보를 모으고, 전체 정렬을 두 차례 수행하여 최종 800개를 고른다.
- posting 순회 중 `getRecord()`가 같은 row의 메타데이터 객체를 반복 생성한다.
- 800개 후보 각각에 대해 query 발음 벡터와 세부 가중치를 반복 구성한다.
- DP·sliding 채점 중 같은 음소쌍의 기본 유사도를 반복 계산한다.
- 검색어가 발음 record에 없으면 `pronunciation_not_found`가 발생한다. V1의 규칙 기반 입력 발음 처리를 잃지 않도록 해야 한다.
- SQLite–Worker 결과 동등성은 같은 V2 알고리즘의 이식 검증이다. V1보다 품질이 좋다는 증거는 아니다.

각 질의는 새 프로세스에서 한 번 초기화하고 cold/warm을 한 번씩 실행했다. 표본이 작아 p95나 일반 성능 보장으로 해석할 수 없다.

| 질의 | 초기화 | cold 검색 | warm 검색 | warm 후보 조회·선별 | warm 재채점 | cap 이전 발음 후보 |
|---|---:|---:|---:|---:|---:|---:|
| 사랑 | 569ms | 885ms | 675ms | 336ms | 338ms | 101,314 |
| time | 663ms | 1,216ms | 1,027ms | 634ms | 393ms | 166,598 |
| 바나나 | 442ms | 1,054ms | 712ms | 321ms | 390ms | 68,511 |

초기화는 cold 검색과 별도 비용이다. cold posting 읽기는 각각 5,930,051 / 12,678,922 / 7,492,574 bytes였고 warm 추가 읽기는 모두 0이었다. 따라서 영구 캐시는 재방문 로딩에 유효하지만 warm 계산 비용까지 해결하지는 못한다. 과거 보고서와는 언어 범위 등이 달라 직접 성능 회귀로 비교하지 않는다.

### 한국어 정확 표기 경계 인덱스 실험

기존 surface bigram의 head 160,194개, pair 1,256,097개를 그대로 사용했다. 길이 1~4의 head suffix → head ID 목록을 구축하고, 같은 query split에서 follower prefix가 정확히 일치하는 결과를 비교했다.

- 12개 고정 질의에서 결과 ID 및 열거 순서가 모두 동일했다. 이 중 4개는 정확 일치 결과가 없는 사례다.
- query별 9회 측정, 실행 순서를 번갈아 배치했다.
- 인덱스 구축 약 189ms, 입력 JSON 파싱 약 605ms. 운영에서는 인덱스 구축을 빌드 시 수행한다.
- posting ID 531,638개를 uint32로 저장할 경우 ID 부분만 2,126,552 bytes. 키·offset·본문·런타임 객체 비용은 별도다.

| 질의 | 정확 일치 수 | 단순 head 순회 p50 | suffix 조회 p50 |
|---|---:|---:|---:|
| 바다 | 2 | 1.096ms | 0.024ms |
| 나비 | 61 | 2.516ms | 1.112ms |
| 에대해 | 4,949 | 5.810ms | 4.384ms |
| 이가 | 2,926 | 4.449ms | 3.594ms |

**이 수치는 전체 V1 검색의 개선 배수가 아니다.** 비교 대상은 간소화한 정확 표기 후보 추출이며 음소 fallback·가중치·최종 순위·영어 연결은 포함하지 않는다. 흔한 조사 경계에서는 follower 순회가 여전히 크므로, suffix 하나만 추가하는 것으로는 충분하지 않다. 오른쪽 prefix와 pair-level 교집합까지 적용할 근거가 된다. 정확 일치가 0인 질의가 있으므로 발음 유사 fallback도 반드시 남긴다.

## 4. 제안하는 정적 검색 구조

```mermaid
flowchart LR
  A[사전·관측된 단어쌍] --> B[오프라인 발음·형태·빈도 처리]
  B --> C[언어별 압축 인덱스와 manifest]
  C --> D[GitHub Pages]
  D --> E[Search Worker]
  E --> F[경계 후보 조회와 pair 교집합]
  F --> G[기존 점수식으로 재채점]
  G --> H[정렬·강조·듣기 UI]
```

### 단어 검색: 결과를 보존하는 최적화부터

1. 언어·빈도·품질·발음 offset을 수치 배열로 두고, 전체 record를 객체로 복원하지 않는다. 문자열은 필요한 결과와 입력 lookup에만 조회한다.
2. 현재 두 정렬의 comparator와 동점 규칙을 그대로 유지하는 bounded top-K 선택을 도입한다. primary를 먼저 확정한 뒤 그 ID를 제외한 exploration을 별도 선택해야 기존 후보를 보존한다.
3. query 벡터·projection·가중치는 요청당 한 번 계산한다. 후보의 음소 ID·offset도 재사용한다.
4. 음소쌍 기본 유사도 표를 미리 만든다. 현재 68개 음소라면 Float64 68×68 표는 약 36KiB다. 사용자 위치 가중치는 이후 적용하여 slider 동작을 유지한다.
5. TypedArray와 재사용 DP buffer로 할당을 줄인다. 초기에는 Float64를 유지하고 Float32·근사 채점은 별도 품질 실험으로 둔다.
6. 필요한 언어와 index key 범위에 맞게 shard를 나눈다. 작은 파일을 무조건 많이 만드는 대신 첫 질의의 파일 수·bytes·metadata 크기를 함께 측정한다.
7. 슬라이더 변경은 준비된 query·후보·발음 데이터를 재사용한다. 이전 Top-50만 재채점하면 가중치 변경 때 새로 떠야 할 결과를 놓친다. 언어·projection·발음모드 등 후보 조건이 바뀌면 후보도 다시 찾는다.
8. 누락 입력은 기존 한국어 규칙 기반 G2P로 보완한다. 영어는 사전·복수 발음·단어/형태 분해를 우선하고, 근거가 약한 추정 발음은 표시한다. 큰 영어 G2P 모델은 측정 없이 기본 다운로드에 넣지 않는다.

### 연결 검색: 왼쪽 단어를 먼저 잘라내지 않는 구조

관측된 두 단어를 `pair_id`, `left_id`, `right_id`, 실제 표기, 발음 후보, 빈도, 출처별 근거, 품사·조사 flag로 저장한다. 모든 단어의 데카르트 곱을 미리 만들지 않는다.

각 query 분할에서:

1. 왼쪽 음소 suffix 인덱스로 첫 단어 후보를 찾는다.
2. 오른쪽 음소 prefix 인덱스로 둘째 단어 후보를 찾는다.
3. left→pair 및 right→pair 인접 목록을 이용해 관측된 연결쌍을 교집합으로 찾는다. 더 선택적인 쪽부터 조회한다.
4. 한국어 정확/부분 표기와 모음열·유사 음소 경로도 합친다. 기존 부분 일치의 longest-overlap 조건과 음소 fallback을 보존해야 한다.
5. 완성된 pair에서 양쪽 발음·빈도·자연스러움을 함께 채점한다. 기존 first top-200 방식은 기준선으로 남기고, pair 단위 선별은 품질 개선 단계에서 평가한다.

공통 음소 ID 체계를 사용하되 언어별 pronunciation·stress·경계 규칙은 보존한다. 영어는 철자 suffix가 아니라 음소 prefix/suffix, 강세 모음과 음절을 조회한다. 복수 발음과 약형을 함께 검토하고, 필요하면 음소 분할을 확장하되 후보 폭을 측정한다.

빈도가 높은 경계에는 정렬된 uint32 posting 또는 bitmap을 사용한다. 희소 posting은 작은 배열이 더 간단할 수 있다. bitmap 교집합은 멤버십 연산이며 기존 retrieval weight·match count를 대체하지 않으므로 점수 신호는 별도 유지한다.

### 연결 검색 품질 개선

- 사전 단어를 따로 읽은 발음과 구문 안에서 이어 읽은 발음을 구분한다. 한국어 연음·비음화·경음화, 영어 약형·강세를 후보 구문에 맞게 검토한다.
- 표기 경계와 음소 정렬을 함께 보관해 어느 구간이 맞는지 표시한다. 표기 일치·발음 일치·느슨한 라임은 구분하되 분류를 곧바로 강제 순위로 사용하지 않는다.
- 자연스러움은 단순 unigram 빈도만 쓰지 않고 관측 pair 빈도·association·출처 다양성·형태 적합성을 함께 사용한다. 기존 점수와 A/B 평가 후 도입한다.
- 한국어 조사 허용은 실제 형태 정보로 판단하고, 조사만 바뀐 결과가 상단을 채우는 현상은 별도 다양성 평가로 다룬다.
- head당 30개 follower 잘림은 검색용 원본 빌드에서 재검토한다. 희귀·고유명사 후보를 무조건 제거하면 라임 품질이 떨어질 수 있다.
- 제외 단어·언어 필터는 Top-K 전에 적용하고, 이미 제외된 결과 때문에 화면이 비는 문제를 막는다.
- 순수 발음과 주제 관련성은 독립된 신호로 유지한다. 의미 벡터가 없는 후보는 무관한 것으로 처리하지 않는다.

| 학습된 char LM·pko-T5 | 검색 runtime에서 제외 권장 | 원하면 소수 후보를 오프라인 평가하는 교사로 시험. 현재 사람 평가·검색 이득 근거가 부족하여 필수 자산으로 두지 않음 |
| 가사 분석·생성 UI/API·ONNX 계획 | 제품 범위에서 제거 | 실제 제거 작업 시 연구 파일과 제품 의존성은 구분하여 정리 |

int8 의미 벡터는 한국어 43,313개, 영어 11,452개로 코퍼스 어휘에 제한되어 있다. 기존 JSON 전체를 이 파일로 바꾸면 주제 검색 커버리지가 줄 수 있다. 양자화 방식은 재사용하되 검색 사전에 맞게 coverage를 다시 확보해야 한다. 한국어·영어 벡터는 서로 다른 학습 공간이므로 직접 cross-language cosine을 계산하지 않는다.

## 6. 오픈소스 조사와 채택 우선순위

아래의 적용 판단은 공식 문서 기능을 이 프로젝트 요구에 맞춰 해석한 제안이다. 타 프로젝트의 벤치마크를 이 앱의 예상 배수로 사용하지 않는다.

|---|---|---|
| [Pagefind](https://pagefind.app/) | 정적 검색 bundle과 부분 로딩용 index chunk | **구조 참고 1순위.** 언어/키별 분할 로딩·결과 지연 로딩을 참고. 음소 가중 DP·연결 pair 검색을 그대로 대체하는 엔진으로 선택하지 않음 |

## 7. GitHub Pages 운영 방식

- 로컬 또는 Actions 빌드가 모든 사전·발음·pair 통계를 정적 바이너리/압축 자산으로 만든다. 브라우저에서 FastAPI나 외부 추론 서버를 호출하지 않는다.
- `public/` 전부가 아니라 검색 UI·Worker·승인된 자산만 배포한다. 생성 API 참조와 외부 실행 스크립트는 제거하고 hangul-js는 버전을 고정해 함께 제공한다.
- app shell, 입력 발음 lookup, 후보 탐색용 최소 metadata를 우선 읽는다. 검색 모드·언어에 맞는 shard를 필요할 때 가져온다. 최초 화면에서 양 언어 전체 데이터를 무조건 읽지 않는다.
- 압축 효과는 실제 Pages 응답으로 측정한다. 서버의 임의 Content-Encoding·Range·COOP/COEP 설정을 전제로 설계하지 않는다. 필요하면 파일 자체 압축과 클라이언트 해제를 사용하되 해제 비용도 포함한다.
- 기본 실행은 단일 Worker + JS/선택적 단일 스레드 WASM으로 구성한다. SharedArrayBuffer·WebGPU·WASM threads를 필수 조건으로 만들지 않는다.
- HTTP cache와 Worker 메모리 cache 후, [Service Worker/Cache Storage](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)로 재방문 자산을 보관한다. HTTPS, `/rhymePJ/` 하위 경로, 해시 버전 분리, 저장소 축출·실패 시 재다운로드를 고려한다.
- 새 manifest 필수 파일 검증이 끝나기 전에는 사용 중인 정상 버전을 바꾸지 않는다. cache가 없어도 온라인 검색은 동작해야 한다.
- 최종 산출물을 `/rhymePJ/` 하위 경로의 정적 서버에서 검증한다. Python API mount를 통한 성공만으로 Pages 배포 가능 판정을 내리지 않는다. 플랫폼 제한은 [GitHub Pages 공식 문서](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)를 따른다.

## 8. 실행 순서와 완료 기준

### 단계 A — 기준선과 제품 범위 정리

생성·분석을 앱에서 제거하고 검색 전용 진입점을 만든다. V1 production과 현재 V2의 실제 검색 함수를 호출하는 고정 benchmark를 구축한다. UI와 다른 간이 검색기로 회귀 통과를 대신하지 않는다.

한국어·영어 각각 단어/연결, 한영 교차, 짧고 흔한 음소, 긴 단어, OOV, 복수 발음, 모음만, 세부 가중치, 주제, 제외 단어, 조사 옵션을 포함한다. 작은 seed만으로 전체 품질을 주장하지 않는다. 추천 첫 평가 규모는 계층화한 200~500개 질의이며 검토 비용에 따라 조정한다.

### 단계 B — 점수 보존 최적화

Worker 이동, 오프라인 발음, 메타데이터 사전 결합, 반복 객체 생성 제거, top-K 선택, query 전처리 cache, 기본 유사도 표를 적용한다. 점수·후보 규칙은 그대로 둔다. Top-K·동점 순서·score 허용오차 1e-6를 확인한다. 한영 교차와 극단적 slider도 포함한다.

### 단계 C — 연결 전용 양방향 인덱스

한국어·영어 suffix/prefix, 표기/음소/모음열, 관측 pair 교집합을 도입한다. 처음에는 기존에 평가하던 후보가 모두 복원되는지를 검사한다. 이후 first top-200 제한을 pair 기준으로 바꾸는 실험은 품질 변경으로 별도 평가한다.

### 단계 D — 전송·캐시·정적 배포

record 이진화, 언어별·선택적 shard, int8 주제 모듈, 버전 cache와 Pages artifact를 만든다. 주요 네트워크 실패·cache 초기화·취소·구버전 교체·브라우저 메모리도 확인한다.

### 단계 E — 발음과 자연스러움 개선

CMU 복수 발음·강세, 한국어 구문 발음, follower coverage, 후보 다양성, 출처별 자연스러움 신호를 사람 평가와 함께 도입한다. 한영 혼합 구문·3어절 이상은 그다음이다.

### 초기 성능 목표안 — 아직 측정으로 달성한 수치가 아님

| 측정 항목 | 첫 목표 |
|---|---|
| warmed 단어 검색 입력→상위 20개 렌더 완료 | p95 150ms 이하 |
| warmed 두 단어 연결 검색 입력→상위 20개 렌더 완료 | p95 300ms 이하 |
| 동일 질의 slider 재채점 | p95 100ms 이하 |
| 초기 UI·필수 lookup 전송 | 압축 후 2MiB 이하 지향 |
| 첫 언어·모드 검색까지 누적 전송 | 압축 후 5MiB 이하 지향 |
| cold 첫 검색 | 고정 데스크톱·20Mbps·RTT 50ms에서 p95 3초 이하 지향 |

네트워크·장치·브라우저 버전을 기록하고 cold(HTTP/SW 비움), 재방문 disk-cache, warm Worker를 분리한다. 각 상태에서 충분한 반복으로 p50/p95와 bytes·요청 수·peak memory·main-thread long task를 함께 기록한다. 위 budget을 맞추기 위해 후보를 조용히 잘라내지 않는다.

품질은 두 단계로 판정한다. 순수 최적화는 기존 실제 함수와 결과 동등성을 요구한다. 알고리즘 개선은 충분히 넓은/offline 완전탐색 결과에 대한 후보 Recall@K와 사람의 라임·자연스러움 판단을 확인한다. 평균 점수가 좋아도 한국어/영어·희귀어·극단 가중치 중 한 구간이 악화되면 별도로 표시한다. 비교 평가 데이터와 최종 검증 데이터는 나눈다.

## 9. 이번 조사에서 수행하지 않은 일

앱 기능 삭제, 운영 코드 교체, 새 라이브러리 설치, 생성 모델 재학습, GitHub 배포는 수행하지 않았다. 새로 추가한 것은 이 조사 문서와 재현 가능한 연구 스크립트이며, 측정 JSON은 기존 ignored `reports/generated/`에 저장했다. 영어 연결의 전체 지연, 실제 Pages 전송, 새 인덱스의 전체 순위 동등성은 후속 구현에서 측정해야 한다.
