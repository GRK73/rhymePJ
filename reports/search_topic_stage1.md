# 연결 라임 주제 검색 1차 개선

2026-09-22. 적용 범위는 정적 연결 라임 검색이다. wordfreq 값, 빈도 점수 함수와 기존 빈도 계수는 유지했다. 단어 검색의 비활성 주제/빈도 기능은 이번 변경 대상이 아니다. 공개 배포는 하지 않았다.

## 동작 변경

- 직접 작성한 한국어 주제 107개의 영어 번역 매핑을 추가했다. 예: 사랑→love, 이별→breakup/separation. 범용 번역기가 아니며, 밤/눈/배 같은 일부 다의어는 임의로 매핑하지 않았다. 모든 주제에 최소 하나의 실제 영어 벡터가 있음을 검사했다.
- 검색 결과 언어에 필요한 벡터만 준비한다. 선택하지 않은 언어의 주제 shard로 활성 여부를 판단하던 로직을 제거했다. 지원하지 않는 언어의 주제는 화면에 안내하고 그 언어에는 기존 무주제 점수식을 적용한다.
- 주제는 알지만 두 후보 단어 중 벡터가 없는 경우, 후보를 삭제하지 않는다. 유사도는 null, 순위 계산에 쓰는 주제 점수는 중립값 50이다. 따라서 결과 수와 순위는 의도적으로 달라질 수 있다.
- 주제 가중치 5의 계수는 기존 0.15를 유지한다. 양수 가중치 w에서는 주제 계수를 0.03w로 설정하고 발음 경계 계수만 조절한다. 빈도 계수는 양수 주제 활성 상태에서 기존 0.08+0.08f, 비활성 상태에서 기존 0.10+0.10f를 유지한다. f는 빈도 slider/10이다.

## 계산 최적화

평균 벡터의 코사인은 다음과 같이 계산한다.

`cos(q, (a+b)/2) = (q·a + q·b) / (||q|| ||a+b||)`

각 단어의 원래 벡터 크기를 유지한다. 단어별 정규화 후 평균으로 바꾸지 않았다. 벡터 조회, 주제-단어 내적, 단어쌍 길이, 주제-단어쌍 결과를 재사용한다. 주제 캐시는 최근 2개, 쌍 결과/길이는 각각 50,000개, 원본 store별 조회 캐시는 100,000개로 제한한다. 원본 store와 벡터는 로드 후 불변으로 취급하며 교체 시 객체 참조가 바뀌어야 한다.

추가로 마지막 검색 조건의 **중복 제거 전 전체 후보**를 최대 50,000행까지 보관한다. 같은 검색어에서 주제나 빈도/주제 가중치만 바뀌면 발음 후보 생성·코퍼스 점수를 반복 계산하지 않고 전체 후보를 재채점한 후 중복 제거와 정렬을 다시 한다. 최종 상위 결과만 캐시하지 않으므로, 다른 분할이 새 가중치에서 우승할 수 있다.

검색어·언어·발음모드·제외어·조사 허용·음소/세부 가중치가 달라지면 후보를 새로 만든다. 캐시 한도를 넘는 결과는 기존 전체 계산을 사용한다. Worker 종료/취소 시 캐시도 해제된다.

## 측정과 추정 수정

코사인 관련 연산만 최적화한 중간 버전에서는 전체 응답 시간이 안정적으로 줄지 않았다. 기존 주제 계산 비중을 20~40%로 놓았던 대화 중 추정은 측정값이 아니며 이 데이터로 확인되지 않았다. 후보 복원으로 한국어 `가커` 결과가 3,321→4,415개로 늘어난 점도 전체 비용에 영향을 준다.

최종 비교는 opt4와 변경 버전을 별도 Chrome 인스턴스에서 번갈아 실행했다. 준비 1회 후 동일 검색 5회 중앙값, 실제 handleSearch와 결과 표시 후 2프레임까지다. 아래는 **동일 검색 조건의 후보 캐시가 준비된 상태**이며 새 검색어·첫 방문 개선율이 아니다.

| 조건 | opt4 표시 ms | 변경 후 표시 ms | 단축 | opt4 계산 → 변경 후 계산 ms |
|---|---:|---:|---:|---:|
| 한국어 사랑, 주제 없음 | 256 | 117 | 54% | 142 → 11 |
| 한국어 가커, 주제 사랑/빈도 5 | 222 | 157 | 29% | 124 → 16 |
| 한국어 바나나, 세부 가중치 | 350 | 89 | 75% | 286 → 6 |
| 영어 flow, 주제 없음 | 48 | 30 | 38% | 22 → 0.4 미만 |
| 영어 time, 주제 love/빈도 5 | 84 | 38 | 55% | 43 → 1 |
| 영어 love, 세부 가중치 | 165 | 57 | 65% | 104 → 2 |

원본: `reports/generated/linked-optimization-1790045757909.json`. Windows 데스크톱 Chrome 153.0.8010.53, 로컬 HTTP, 네트워크/CPU 제한 없음. 작은 표본이고 환경 변동이 있다. 모바일, 실제 Pages, p95, 메모리 또는 최초 로딩 개선을 증명하지 않는다.

한국어 주제 사랑→영어 time 검색은 이전 0개에서 874개로 복원됐다. 이 경우 서로 다른 작업량이므로 예전 0개 결과와 비교한 속도 개선율은 제시하지 않는다. 한국어 주제/전체 언어 및 미등록 주제도 브라우저에서 확인했다.

## 검증

- Node 검색 테스트 31개 통과. 코사인 4,800조합 오차 1e-12 이내, 0/5/10 가중치, 빈도 계수 보존, 미등록/다의어/누락 벡터, 캐시 예산·주제/원본 교체 검증 포함.
- 실제 전체 Worker 순회: 기존에 있던 후보가 모두 남고 빈도 점수가 동일함을 확인. 주제 가중치 5의 최대 점수 오차 1.42e-14, 유사도 오차 4.44e-16.
- 한국어·영어의 주제/빈도/제외어/음소 가중치 16조건에서 캐시 재채점과 강제 재계산의 전체 결과 JSON이 일치했다. `reports/generated/semantic-profile-1790045641325.json`.
- 위 Node VM 보고서는 정확성 및 계측용이다. 다른 검사가 겹친 실행이므로 그 파일의 시간으로 브라우저 속도 개선율을 계산하지 않는다.
- 프로젝트 검사, 기존 연결 발음 검사 20/20 통과.
- 실제 Chrome에서 취소·검색어 변경·Worker 오류 복구·최신 요청 우선·모드 전환 검증 통과, 자동 API 요청 0회. `reports/generated/linked-worker-smoke-1790045846431.json`.
- 현재 작업 공간에는 `indexes/phoneme/v0/static/search-manifest.json`이 없어 전체 정적 미리보기 staging은 실행할 수 없었다. 연결 기능은 `/rhymePJ/`의 실제 소스·자료를 읽는 로컬 서버로 검사했다. 단어 자산 생성·전체 배포 검증을 완료한 것으로 보지 않는다.

## 모델 교체 준비와 미완료 항목

현재 브라우저는 기존 50차원 벡터를 사용한다. Gemma/Potion 교체, int8 자산 전환, 자주 쓰는 주제의 사전 점수 파일은 아직 적용하지 않았다.

`configs/topic_model_comparison_v1.json`과 `scripts/search/compare_topic_models.py`에 Gemma 128차원/Potion 256차원 비교 설정과 오프라인 실행기를 준비했다. 단어·문장 주제 12개의 소규모 직접 작성 screening이며 사람 평가나 실제 라임 품질 평가를 대체하지 않는다. float/int8 결과 순위를 함께 기록하고, 브라우저 자산을 자동 교체하지 않는다.

이 환경의 기존 `.venv-transformers4`는 기반 Python 경로가 없어 실행되지 않았고, 별도 번들 Python에는 추론 라이브러리가 없다. 실행기의 `--describe`만 확인했다. 실제 모델 추론/품질 수치는 아직 없다. Gemma는 모델 저장소 이용 조건 수락도 필요하다. 라이브러리와 모델을 준비한 뒤 별도 홀드아웃 라임 후보, 주제 연상·다의어·신조어, phrase 직접 임베딩 대 단어 평균, 데이터 크기·첫 로딩으로 검증해야 한다.
