# 연결 검색 최적화 opt1

2026-09-20. 한국어·영어 연결 검색의 반복 계산을 줄였다. **데스크톱 반복 검색 6개 설정에서 결과 표시 시간 중앙값이 50~68% 감소**했고, 비교한 전체 결과·점수·순서는 일치했다. 단어 검색 엔진이나 최초 다운로드 최적화까지 완료한 것은 아니다.

## 변경

`public/js/search/linked-cache.js`에 다음 캐시를 추가했다.

1. 언어별 사전 배열과 단어→항목 Map을 재사용한다. 원본 순서 및 중복 단어의 마지막 항목을 선택하는 기존 동작을 보존한다. 사전 객체가 교체되면 다른 캐시를 사용한다.
2. 정적인 발음 후보 배열과 한국어 surface 사전의 `Object.entries()` 결과를 재사용한다. 매 검색/분할마다 전체 자료구조를 다시 만들지 않는다.
3. 경계에서 비교하는 **동일 음소 구간**은 한 번 채점하고 재사용한다. 위치별 가중치와 분할 입력이 다른 캐시는 분리한다. 결과의 일치 음소 위치는 원래 단어 내 위치로 복원한다.
4. 요청마다 새로운 점수 캐시를 만들고, 분할이 바뀌면 이전 캐시를 해제한다. 보관하는 점수 항목은 최대 32,768개이며 초과하면 기존 계산으로 처리한다. 가중치 변경 시 이전 점수를 사용하지 않는다.

후보 수·선별 임계값·최대 첫 후보 200개·정렬/동점 규칙·주제/빈도 점수식은 바꾸지 않았다. 전체 검색 결과를 캐시해 같은 검색에만 빨라지는 방식도 아니다. 요청마다 필요한 계산을 다시 수행하되, 해당 요청의 서로 다른 단어들이 공유하는 발음 구간 계산을 재사용한다.

사전과 발음 자산은 Worker가 살아 있는 동안 변경하지 않는다는 현재 계약을 전제로 한다. 이후 자산의 제자리 수정 기능을 추가한다면 캐시 무효화도 구현해야 한다. 정적인 사전용 캐시의 크기는 데이터 크기에 비례하며, 32,768 제한은 요청의 점수 캐시에 대한 값이지 전체 메모리 제한이 아니다.

## 반복 성능 측정

기준선은 최적화 직전 소스 24파일을 보존한 `tests/reference/worker-v1/`이다. `scripts/search/benchmark_linked.mjs`가 같은 정적 데이터의 SHA-256을 확인하고 실제 브라우저 `handleSearch()`를 실행한다.

- 환경: Windows, Intel Core 5 120U, Node 24.13.1, Chrome 153.0.8010.48, 1600×1000 headless 브라우저.
- 엔진마다 설정별 준비 검색 1회 후 측정 5회. 기준선/현재 엔진 실행 순서를 번갈아 바꾸며 순차 실행한다.
- 표의 값은 5회 중앙값. 시작부터 결과 렌더링 후 두 번의 animation frame까지 포함한다.
- 주제/빈도 사용 설정은 둘 다 5. 기본 설정은 빈도 1/주제 0. 세부 설정은 `[8, 0.5, 3, 7, 1.5]` 반복이며 한국어는 첫 조사 허용도 켠다.
- 모든 준비/측정 실행에서 전체 결과 JSON 해시가 같다. 같은 입력 자산과 같은 옵션으로 비교했다.

| 설정 | 입력 | 변경 전 표시 ms | 변경 후 표시 ms | 감소 | 변경 전→후 Worker 계산 ms |
|---|---|---:|---:|---:|---:|
| 한국어 기본 | 사랑 | 444 | 144 | 68% | 399→85 |
| 한국어 주제·빈도 | 가커 / 주제 사랑 | 376 | 188 | 50% | 279→65 |
| 한국어 세부+주제·빈도 | 바나나 / 주제 사랑 | 1,742 | 641 | 63% | 1,671→521 |
| 영어 기본 | flow | 332 | 113 | 66% | 318→81 |
| 영어 주제·빈도 | time / 주제 love | 506 | 229 | 55% | 456→165 |
| 영어 세부+주제·빈도 | love / 주제 love | 658 | 265 | 60% | 583→199 |

표시 시간과 Worker 계산 시간은 각각 중앙값을 구하므로 두 열의 차이를 정확한 전송 시간으로 해석하지 않는다. 작은 표본의 데스크톱 warm 측정이며 p95, 모든 질의의 속도, 모바일 성능, Pages 최초 진입 시간에 대한 보장은 아니다.

최종 원본 보고서: `reports/generated/linked-optimization-1789908543598.json`. 기준/현재 소스 manifest, 데이터 해시, 브라우저 버전, 각 회차의 결과 해시·표시/계산 시간·캐시 통계를 포함한다. `linked-optimization-1789908406247.json`은 캐시 수명 보완 전의 탐색 실행이며 최종 수치에 사용하지 않았다.

계산 감소 예시(최종 warm 실행 1회):

- 한국어 `사랑`: 실제 점수 함수 호출 2,438회, 같은 구간 재사용 64,504회.
- 영어 `time` + 주제: 실제 호출 1,263회, 재사용 297,606회.
- 한국어 세부 설정: 실제 호출 29,291회, 재사용 396,183회. 한 분할의 최대 보관 항목 26,956개.

`score_calls`는 점수 함수 호출 횟수이며 내부 빠른 반환도 포함한다. 모두 DP 행렬 계산 횟수라고 해석하지 않는다.

## 남은 한계

- 첫 실행의 사전·연결 자료·주제 벡터 다운로드/파싱은 남았다. 최종 UI smoke의 첫 주제 연결 검색은 약 5.2초였고, 화면 타이머 최대 간격도 약 310ms로 관측됐다. 이번 warm 가속만으로 첫 진입의 끊김이나 로딩이 해결됐다고 주장하지 않는다.
- 취소 후 Worker를 다시 만들면 자료를 재준비한다. 원본 전체 결과 전달과 페이지/Worker의 사전 중복 보유도 남아 있다.
- 단어 검색의 주제/빈도 복원 및 연결 주제 slider의 기존 고정 계수 수정은 아직 하지 않았다. **현재 사용되는 가중치 계산을 보존한 상태에서도 연결 검색을 가속**한 것이다.
- 새 양방향 연결 인덱스, 정적 바이너리/전송 크기 축소, 품질 개선, 공개 Pages 배포는 후속 작업이다. 서버 없이 정적 Worker로 실행되는 조건은 유지했다.

## 재현

```bash
npm run benchmark:linked
npm run test:search
npm run smoke:linked-ui
npm run smoke:static-ui:v2
```

Node/Chrome, `npm ci` 의존성 및 현재 정적 데이터가 필요하다. 이번 환경에서는 npm 실행 경로 문제로 해당 Node 스크립트를 직접 호출했다. 데이터나 코드가 바뀌면 생성 보고서의 source/input 해시를 확인하고 새로 측정해야 한다.
