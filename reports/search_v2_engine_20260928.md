- 작성일: 2026-09-28
- 기준 설계: `V2검색엔진설계.md`
- 범위: §10의 1~3단계(사전 빌드, 채점 커널, 검색 과정)와 발음 데이터, 검색어 발음 변환

## 1. 발음 데이터: Heami

Windows 내장 한국어 음성 **Microsoft Heami Desktop**이 읽을 때 보고하는 음소 이벤트(`PhonemeReached`)로 발음기호를 만들었다. 음성 인식은 거치지 않으며, 단어당 약 6ms 걸린다.

| 항목 | 값 |
|---|---|
| 대상 | V1 사전 250,632 + 가사 코퍼스 136,616 = **387,248단어** (한국어 243,093 / 영어 144,155) |
| 방식 | 단어당 발음 1개로 대체. 받침 살림(`국가` → `k u k k* a`, 복원 8,441곳) |
| 영어 외래어 | 외래어 표기가 있는 2,984개는 그 한글 표기를 Heami가 읽은 발음 사용 |
| 영어 정확도 | 외래어 표기 정답 2,983개 기준 음소 오류율 17.6% (기존 규칙 56.0%) |
| 한국어 | 기존 표준발음 규칙과 88.3% 일치. 불일치는 한자어 경음화·ㄴ첨가·격음화 등 Heami가 맞는 경우가 많음 |

빈도는 V1 방식을 그대로 썼다. 한국어는 kowikitext 정확 일치 횟수, 영어는 wordfreq다. V1에 있던 단어 257,334개는 V1 값과 **모두 같다**. 한국어 190,269개와 영어 141,882개에 빈도 값이 있고, 나머지는 V1 기본값(1.0)을 쓴다.

## 2. 검색어 발음: Heami 모방 모델

브라우저에서는 Heami를 실행할 수 없다. 그래서 사전에 없는 검색어는 Heami 결과로 학습한 모델로 바꾼다.

| 모델 | 학습 쌍 | 시험 단어(학습 제외) | Heami와 완전 일치 | 음소 오류율 | 기존 규칙 |
|---|---:|---:|---:|---:|---|
| 한국어 | 218,891 | 12,046 | **95.8%** | **0.68%** | 87.2% / 1.83% |
| 영어 | 129,743 | 7,258 | **66.0%** | **8.7%** | 1.1% / 64.5% |

- 구조는 양방향 GRU + 어텐션, 약 125만 파라미터다. 모델 파일은 언어별 5MB다.
- 브라우저 추론(`public/js/search/g2p-heami.js`)은 순수 JavaScript이고, PyTorch 결과와 **한국어·영어 각 2,000/2,000 동일**하다. 단어당 13~31ms 걸린다.
- 영어의 남은 오류는 Heami가 짧은 단어를 철자로 읽는 경우(`hz`, `ahh`)가 많다. 모델이 오히려 자연스러운 경우도 있다(`bus`: Heami 뻐스, 모델 버스).
- 예시: `서울역` → 서울력, `킹받네` → 킹반네, `skibidi` → 스키비디, `flowzzzz` → 플라우즈즈

검색어 처리(`public/js/search/word-query.js`):
1. 사전에 있는 단어는 저장된 발음을 쓴다. 결과 단어와 같은 방식이다.
2. 사전에 없는 단어는 모방 모델로 바꾼다.
3. 자모(`ㅋㅋ`, `ㅏㅏ`)는 V1 자모 규칙을 쓴다.
4. 띄어쓰기, 문장부호, 문자 종류가 바뀌는 곳에서 나눠 처리한다(`사 랑`, `사랑!`, `ice cream`, `사랑love`). 악센트는 없앤다(`café` → `cafe`).

## 3. 검색 엔진

`public/js/search/word-engine.js`는 V1 `calculateScore`와 같은 식(가중 DP + sliding window)으로 사전 전체를 계산한다. 그 뒤 V1과 같은 식으로 40점 기준, 빈도, 주제를 적용한다. §9에서 결정한 대로 숨은 보정은 없다.

- **동점 규칙:** 점수를 소수점 셋째 자리로 반올림한 값이 같으면 가나다·abc순이다. V1의 "차이 0.001 이하"는 추이성이 없어 같은 입력에서도 순서가 흔들렸기 때문에 바꿨다. 설계서에 반영했다.
- **사전 파일:** `public/assets/lexicon/v1/` (gzip 8.5MB, 설계 목표 3MB 초과, §5 참고). 빌드 후 저장본에서 다시 읽어 같은 검색 결과가 나오는지 검증한다.

### V1 동일성 검증

기준은 V1 원본 코드(`5df2ae8`)를 그대로 실행하되 §9에서 없앤 보정만 끈 것이다. 엔진에는 같은 V1 발음 후보를 넣었다.

| 묶음 | 결과 |
|---|---|
| 한국어 단어 80 | 80/80 |
| 영어 단어 80 | 80/80 |
| 교차 언어 40 + 경계 사례 38 | 78/78 |
| 추가 설정 48 (발음 기준 3종, 빈도 0/10, 모음 0, 자음 5, 세부 가중치, 단어 배제) | 48/48 |
| 주제 12 (`--topic`: 한·영 주제, 가중치 1/3/5/10, 언어 3종, 매핑 없는 주제, 벡터 없는 주제) | 12/12 |
| **합계** | **298/298 동일** (결과 단어, 순서, 점수) |

중간에 나온 실패는 모두 기준 쪽에 V1의 숨은 선택 규칙이 남아 있던 탓이었다.
- 0.001 안에서 끝 라임 점수 등으로 발음 후보를 고르는 규칙
- 중복 사전 항목에서 처음 것을 유지하는 규칙
- 빈도 식의 곱셈 순서

기준을 고친 뒤 해당 사례는 점수 차이 0으로 일치했다. 처음부터 통과한 사례는 고치기 전 기준으로 확인한 것이다.

## 5-1. 주제: LaBSE 한·영 공통 의미 공간 (2026-09-28 추가)

V1 방식은 한국어 벡터와 영어 벡터가 따로라서, 한국어 단어는 한국어 주제와만 비교할 수 있었다. 그래서 영어 주제로 한국어만 검색하면 결과가 0개였고, 한국어 사전 단어의 65%(243,093개 중 158,000개)는 벡터가 없어 주제를 켜면 빠졌다.

| 방법 | 한→영 번역 104쌍, 1위 / 10위 안 |
|---|---:|
| 기존 벡터를 외래어 표기 2,612쌍으로 회전 정렬(Procrustes) | 2% / 3% |
| LaBSE (상위 3만 단어 후보) | 69% / 94% |

- **자산:** `scripts/semantic/embed_labse.py`로 사전 387,248단어를 LaBSE(768차원)로 계산했다(CPU 26분, `data/derived/semantic_labse/v0/`). `build_topic_vectors.py`로 평균을 빼고 96차원으로 줄여 행마다 int8로 저장했다(`public/assets/topic/v1/`, gzip 33.6MB, 기존 한·영 주제 벡터 35MB). 압축 전 벡터와의 점수 상관은 0.973, 관련 단어 상위 1000개는 88%가 유지된다. `topic.json`에 만든 사전의 해시를 적고, Worker는 다른 사전용 벡터를 거부한다. (이후 PCA128 4비트, 18.8MB로 바꿨다. §8 참고.)
- **점수 분포:** 평균을 빼면 무관한 단어는 0 근처(하위 5% −0.16, 상위 5% 0.18), 관련 단어는 0.8~1.0이다(사랑↔love 0.98, 애정 0.90, 돈↔현금 0.79). V1 감점식을 그대로 쓰며 가중치 10에서 무관한 단어 약 35%, 관련 단어 약 3%가 깎인다. 따로 보정하지 않는다.
- **동작:** 주제어는 사전 단어여야 한다(한글이면 한국어, 아니면 영어 사전에서 찾음). 없으면 주제 없이 검색하고 "주제어가 사전에 없어 주제 없이 검색"이라고 알린다. 번역표와 Google 번역은 단어 검색에서 빠졌다(연결 검색은 아직 기존 방식).
- **화면 확인:** `time` + 주제 `사랑` → valentine, d'amour, 사랑따윈 등 한·영이 함께 올라온다. `사랑`(한국어만) + 주제 `money` → 돈자랑, 돈가방(V1 방식이면 0개). 새 주제 계산 포함 재채점 0.11초, 주제 자료 첫 로딩 포함 0.86초.
- **V1 동일성 검사(`--topic`)** 는 V1 방식 주제 경로(연결 검색이 쓰는 `semantic.js`)의 기록으로 남는다.

## 5-2. 연결 검색 전환 (2026-09-28 추가)

연결 검색도 단어 검색과 같은 Worker·사전·발음·주제 벡터를 쓰도록 새 엔진(`public/js/search/linked-engine.js`)으로 바꿨다. 사용자 결정(2026-09-28): 영어 발음 기준 선택 가능, 힙합·구어 말뭉치 가산 제거, 글자 일치 우선 제거(발음만 비교), 분할 균형 보정 제거.

- **데이터:** 한국어 연결 표면형 329,288개(첫 단어 160,194개, 연결 1,256,097쌍)를 전부 Heami로 읽었다(새로 추출 240,868개, 3.5ms/단어, 누락 0). 빈도는 단어 사전과 같은 kowikitext 정확 토큰 수(313,812개에 값), 뜻 벡터는 원형(사랑을 → 사랑) 기준이며 사전에 없는 132,757개는 LaBSE로 따로 계산해 같은 평균·기저로 투영했다(`topic/v1/vectors-linked.bin.gz`, 11.5MB, 연결 검색에서 주제를 쓸 때만 받음). 영어는 연결 57,082개 첫 단어·565,371쌍이 모두 사전 단어라 사전의 실제 영어·한국식 발음을 그대로 쓴다. 자산 `public/assets/linked/v2/`는 gzip 18.5MB(기존 연결 자산은 사전·말뭉치 합계 약 35MB + 주제 36MB).
- **분할:** 한국어 검색어는 쓰인 음절 사이에서만(한 음절이면 분할 없음, V1과 같음), 발음은 단어 검색과 같은 음절 대응표로 나눈다. 영어는 V1 규칙(모음 옆, 4음소 초과면 양쪽 2음소 이상). 발음 기준에 따라 실제 영어/한국식 검색어 발음마다 따로 나눈다.
- **점수:** 양쪽 경계 점수(단어 검색과 같은 커널)가 모두 40 초과인 쌍만. 발음 점수 = 양쪽 점수를 소리 수(세부 가중치 합)로 가중 평균. 그다음은 단어 검색과 같다(사용자 결정, 2026-09-28): 빈도는 두 단어 zipf 평균에 V1 빈도식, 주제는 두 단어 뜻 평균의 유사도로 V1 감점식(최대 70%, 벡터 없으면 제외). 연결 빈도는 후보 선정에만 쓰고 점수에서 뺐다(V1 식은 연결 빈도 25%·단어 빈도 10% 고정). 연결 자산에서 연결 횟수·점수를 빼 gzip 18.5MB → 10.2MB. 동점은 한국어 쌍 먼저, 가나다·abc순.
- **V1과 다른 점(결정 외):** V1은 분할마다 첫 단어 후보를 끝소리 점수 상위 200개로 잘랐다(동점이면 파일 순서). 숨은 선택이라 없앴고 모든 쌍을 계산한다. 영어 경계도 한국어처럼 소리 수 가중 평균으로 맞췄다(V1 영어는 단순 평균).
- **속도(Node, 반복 검색):** 사랑해 한국어 0.1~0.3초, whatever 영어 0.6~1.4초, 사랑해 전체 0.9초, time 전체 1.7초. 빈도·주제만 바꾸면 0.04~0.2초. 첫 연결 검색은 자산 로딩 포함 약 1.4초. V1은 사랑해 2.3초, whatever 0.8초(200개 제한).
- **결과 예(연결 빈도 제거 전):** 사랑해 → [사랑 때]문에, 짝[사랑 했]던, 뇌[사 상태]에 (V1: [사망 생]존, 이[사장 취]임). 맛있다 → 수[만 있다]면. money(한국식) → boman irani, osama bin.

구조는 그대로 두었다(검색 자산은 Git 밖 Release zip으로 공급, SHA-256 고정, 사람이 검토한 허용 목록만 조립, 산출물 최종 검사). 옛 엔진 전제(정적 색인 `indexes/phoneme`, parity attestation, 연결 v1 자산, Python 패키지 설치)를 V2 자산 네 종으로 바꿨다.

## 10. 최종 점검 (2026-09-28)

시험 전체, 사이트가 참조하는 파일, 브라우저 시나리오(단어·연결, 한/영/혼합/자모/숫자/악센트/기호, 주제 한↔영·사전 밖 주제, 모음만, 세부 가중치, 배제, 재정렬, 페이지, 취소, 휴대폰 폭), 배포 시험 운행을 다시 확인했다. 고친 것:

| 문제 | 원인 | 수정 |
|---|---|---|
| 취소 뒤 "더 보기"가 취소한 검색의 결과를 이어 붙임 (재현: hello 결과 뒤에 '바람이 분다' 65% 결과) | Worker가 마지막으로 끝난 검색 하나만 페이지용으로 들고 있었고, 취소는 Worker에 전달되지 않음 | 결과에 검색 번호(`searchId`)를 붙이고 페이지 요청은 그 번호로만 받음. 취소는 Worker에 알려 결과를 보관하지 않음. 최근 두 검색을 보관해 취소 뒤에도 화면의 목록이 이어짐 |
| 느린 다운로드를 기다리던 이전 검색이 뒤늦게 끝나 새 검색의 페이지 상태를 덮어씀 | 같은 원인 | 더 새 검색이 시작됐거나 취소된 검색은 계산 전에 멈춤(`search_superseded`/`search_cancelled`) |
| 배경 탭에서 열면 탭을 볼 때까지 "불러오는 중"에 머묾(사전 미리 받기도 시작 안 됨) | 로딩 화면 종료가 `requestAnimationFrame`만 기다림(숨은 탭에서는 멈춤) | 100ms 타이머를 함께 걸어 먼저 오는 쪽으로 종료 |
| 숫자 검색어(`123`)가 엉뚱한 발음으로 검색됨 | 영어 발음 모델이 숫자를 거의 배우지 않음(사전에 숫자 섞인 단어 14개) | 사전에 없는 숫자만의 토큰은 빼고 알림(`숫자(123)는 읽는 법이 여러 가지라 뺐습니다`). 읽는 법을 추측하지 않음. 사전 단어(y2k, 3d)는 그대로 |
| 시간 제한 시험이 가끔 실패 | 40ms 제한·25ms 간격이 Windows 타이머 오차(~15ms)에 걸림 | 200ms 제한·120ms 간격으로 여유 |
| `HeamiG2P.load()`가 없는 파일(`manifest.json`, `weights.bin`)을 가리킴 | 쓰이지 않는 옛 코드 | 삭제 |

- **확인했지만 V1과 같아 두는 것:** sliding window 때문에 긴 단어 일부가 맞아도 높은 점수(love → 글러브·oceanography), 세부 가중치를 켜면 모음·자음 가중치 대신 슬라이더를 씀, 휴대폰 폭에서 설정 칸이 검색창보다 위에 옴.
- **V1 동일성 검사 시간:** 기준값이 V1 엔진 자체(25만 단어를 평범한 JS로 전부 계산)라 한국어 사례 15~20초, 영어 사례 100~130초, 298개를 한 줄로 돌리면 약 6시간이었다. worker thread 6개로 나눠 돌리고, V1 결과를 사례별로(정확한 단어·순서·점수의 SHA-256) `build/parity-cache/`에 바로 저장하게 바꿨다. 이 노트북(Core 5 120U)에서는 스레드당 느려져 약 3배 빨라지고, 다음 실행부터는 V2만 계산해 몇 분이면 된다. 캐시 키는 V1 커밋·기준 코드·사례를 포함하고, 캐시와 다르면 V1을 다시 돌려 실제로 비교한다(변조 시험으로 확인).
