# 초기 로딩 최적화 opt2

2026-09-21. opt1의 반복 검색 가속에 이어 초기 자료 준비의 순차 대기를 줄였다. **로컬 새 브라우저 측정에서 준비+첫 주제 검색 중앙값이 한국어 약 15%, 영어 약 10% 감소**했다. 데이터 파일이나 점수식은 변경하지 않았다.

## 구현

- `public/js/search/linked-data.js`: 원본 사전(약 33.1MB), 외래어, 합성어 발음 자료의 다운로드·파싱을 `Promise.all`로 시작한다. 완료 전에는 준비된 사전으로 공개하지 않는다. 여러 호출은 같은 초기화 Promise를 공유하며 필수 사전 실패 시 재시도할 수 있도록 Promise를 해제한다. 선택 자료가 없을 때의 기본 동작도 유지한다.
- `public/workers/linked-worker.js`: 기존에는 연결 자료 → 코퍼스 보정 → 주제 벡터 순으로 기다렸다. 이제 이들 독립 자료를 병렬로 준비하고 전부 완료한 뒤 동일한 후보 계산을 실행한다. 주제를 비우거나 가중치를 0으로 두면 주제 벡터는 요청하지 않는다.
- 취소 시 Worker 종료, 새 검색 우선, 기존 점수 캐시는 유지한다. 버전 query를 갱신해 이전 runtime/loader 재사용을 방지한다.

병렬화는 용량 절감이 아니다. 한국어/영어 주제 벡터 JSON은 각각 약 53.6MB/45.7MB이며, 화면과 Worker가 큰 사전을 중복 보유하는 구조도 남아 있다. 새 인덱스·파일 분할·바이너리 변환·정밀도 변경은 적용하지 않았다.

## 첫 검색 측정

기준선: `tests/reference/opt1/`에 고정한 최적화 직전 소스 25파일. 도구: `scripts/search/benchmark_linked_startup.mjs`.

- 각 실행마다 새 Chrome 프로필을 사용한다. 한국어 `가커`/주제 `사랑`, 영어 `time`/주제 `love`를 빈도=5, 주제=5로 검색한다.
- 엔진별 3회, 실행 순서를 번갈아 변경한다. 준비용 검색은 없다.
- `준비`는 페이지 이동부터 `isReady` 확인까지, `검색`은 실제 `handleSearch()` 시작부터 결과 표시 후 두 번의 animation frame까지다. `합계`는 두 구간의 합이며 테스트 컨트롤 입력 시간은 제외한다.
- Windows/Core 5 120U/Chrome 153.0.8010.48, loopback HTTP. 기준선 서버는 파일 해시를 검사하고 `no-store`로 제공한다. 실제 GitHub Pages 캐시·인터넷 전송·모바일 조건은 재현하지 않았다.

| 언어 | 항목 | opt1 중앙값 ms | opt2 중앙값 ms |
|---|---|---:|---:|
| 한국어 | 페이지 준비 | 1,089 | 936 |
| 한국어 | 첫 연결 검색 | 4,520 | 3,787 |
| 한국어 | 준비+검색 합계 | **5,592** | **4,765** |
| 영어 | 페이지 준비 | 1,115 | 924 |
| 영어 | 첫 연결 검색 | 2,791 | 2,574 |
| 영어 | 준비+검색 합계 | **3,905** | **3,499** |

각 항목의 중앙값을 따로 구하므로 준비 중앙값+검색 중앙값과 합계 중앙값은 다를 수 있다. 3회라는 작은 표본이므로 p95나 모든 기기에서의 개선율로 일반화하지 않는다. opt1의 50~68% warm 개선율과 이 표의 개선율을 더하거나 곱하지 않는다.

원본: `reports/generated/linked-startup-1790002026476.json`. 총 12번의 실행에서 언어별 전체 결과 SHA-256과 소비한 입력 파일 SHA-256이 모두 일치했다. 각 실행의 source manifest, 파일 해시, 브라우저 버전, 개별 시간도 보관한다.

## 검증과 재현

```bash
npm run benchmark:linked-startup
npm run test:search
npm run smoke:linked-ui
npm run smoke:static-ui:v2
```

검색 Node 테스트 20개에는 기존 점수 캐시/경계 15,552개 비교, 취소·복구, 새 병렬 로더의 동시 시작/준비 완료 시점/Promise 공유/필수 파일 실패 후 재시도를 포함한다. 20개 모두 통과했고 프로젝트 검사도 통과했다.

- 실제 브라우저에서 한국어·영어 각 1개 질의에 기본 설정과 빈도/주제 0·5·10의 조합을 적용한 총 20개 실행은 기존 local-v2 결과와 점수·순서까지 완전히 일치했다. 원본: `reports/generated/search-reference-current-opt2-weights.json`, 비교: `reports/generated/search-opt2-parity-weights.json`.
- 연결 검색 UI의 취소, Worker 실패 후 복구, 이전 요청 무시, 모드 전환 검사를 통과했다. 외부 API 요청은 0회였다. 원본: `reports/generated/linked-worker-smoke-1790002222246.json`.
- 정적 페이지의 단어 검색, 세부 모음 가중치, 진행 표시, 취소 검사도 통과했다. 이 검사는 단어 검색의 비활성화된 주제/빈도 기능을 검증한 것은 아니다.

이번 환경에서는 npm 실행 경로 문제로 위 명령의 Node 스크립트를 직접 실행했다. Python API나 외부 모델 서버는 사용하지 않았다.

## 후속 범위

데이터를 읽기 전에 검색을 시작하는 UI의 기존 경계 동작, 실제 모바일/느린 회선, 처음 받는 파일 크기·파싱·최대 메모리를 더 측정해야 한다. 단어 검색의 주제/빈도 기능 복원, 연결 주제 가중치 수식 수정, 대형 의미 자산 분할과 공개 Pages 배포도 아직 남아 있다.
