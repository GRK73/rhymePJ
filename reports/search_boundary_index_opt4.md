# 연결 후보 발음 인덱스 — opt4

2026-09-22. opt3 다음 단계로 앞 단어 후보의 끝 발음 구간을 미리 묶었다. 검색어별 답을 캐싱하는 방식이 아니므로 처음 입력하는 검색어에도 적용된다. 사전·코퍼스·점수식·주제/빈도 가중치·first-200 후보 정책은 유지한다.

## 구현 범위와 보존 규칙

- 한국어 표제어 160,194개와 영어 사전 행 148,075개에 대해 끝 1~4음소 → 원래 행 ID 목록을 빌드한다. 한국어 표기 끝 글자 → 행 ID 목록도 만든다. 여러 발음 후보가 있으면 모든 구간에 등록한다.
- 실행 중에는 구간마다 기존 `calculateScore()`를 그대로 호출한다. 40점 초과 구간의 행만 모으고 원래 ID 순서를 복원한다. 한국어는 표기 일치 후보와 합집합을 만든 뒤 기존 조사·제외어·정확/부분 일치 정책을 적용한다.
- 정확한 음소 일치만 고르거나 임의의 top-N으로 인덱스를 자르지 않는다. 0/세부 가중치와 동점 순서를 보존한다. 예를 들어 한국어 끝 2음소는 563구간, 영어는 916구간을 채점한다.
- 끝 구간이 5음소 이상이면 기존 전체 순회로 돌아간다. 뒷단어의 시작 발음 계산은 기존 구간 점수 캐시를 사용한다. 전체 pair를 양방향 인덱스로 결합하는 방식까지 구현한 것은 아니다.
- 필요한 언어·구간 길이의 파일만 Worker에서 읽는다. gzip 파일은 해시·길이를 검사하며 재검색에서 재사용한다. 생성물은 `public/assets/linked-index/v1/`에 두고 Git에서는 제외한다. 9파일의 압축 크기는 합계 약 4.33MB다.

## 반복 검색 측정

기준은 `tests/reference/opt3/`의 소스 26파일이다. Windows/Core 5 120U/Chrome 153, loopback HTTP에서 엔진별 준비 검색 1회 후 5회씩 번갈아 측정했다. 실제 `handleSearch()`와 결과 표시 후 animation frame 두 번까지의 중앙값이다.

| 설정 | opt3 표시 ms | opt4 표시 ms | opt3 계산 → opt4 계산 ms |
|---|---:|---:|---:|
| 한국어 `사랑`, 기본 | 476 | 361 | 318 → 212 |
| 한국어 `가커`, 주제·빈도 5 | 410 | 331 | 259 → 172 |
| 한국어 `바나나`, 세부 가중치 | 849 | 767 | 767 → 523 |
| 영어 `flow`, 기본 | 164 | 63 | 137 → 25 |
| 영어 `time`, 주제·빈도 5 | 246 | 78 | 208 → 47 |
| 영어 `love`, 세부 가중치 | 248 | 94 | 213 → 53 |

한국어 표시 시간 약 10~24%, 영어 약 62~68% 단축. 준비 검색을 포함한 72회 실행의 조건별 전체 결과 해시가 일치했다. 원본은 `reports/generated/linked-optimization-1790042402507.json`이며 소스 manifest·입력 해시·브라우저 정보·개별 시간·그룹/후보 카운터를 함께 기록했다.

한국어 `가커`에서는 160,194행 대신 563개 발음 구간을 채점하고 음성 기준 45,167행을 반환했다. 여기에 표기 일치 후보를 합치므로 45,167은 최종 출력 수가 아니다. 영어 `flow`는 148,075행을 916구간으로 채점하고 40,408행을 반환했다.

## 첫 검색 측정

별도 새 Chrome 프로필로 각 설정·엔진을 3회씩 번갈아 실행했다. 기존 opt3와 준비+첫 검색 시간을 비교하며 인덱스 다운로드 비용을 포함한다.

| 조건 | opt3 합계 ms | opt4 합계 ms | 데이터 MB opt3 → opt4 |
|---|---:|---:|---:|
| 한국어 `가커`, 주제 `사랑` | 3,618 | 3,003 | 46.56 → 47.47 |
| 영어 `time`, 주제 `love` | 1,617 | 1,573 | 23.65 → 24.44 |
| 한국어 `가커`, 주제 없음 | 3,345 | 3,036 | 27.31 → 28.22 |
| 영어 `time`, 주제 없음 | 1,289 | 1,122 | 7.03 → 7.82 |

24회 실행 모두 조건별 전체 결과 해시가 일치했다. 원본: `reports/generated/linked-startup-1790042522030.json`. MB는 1,000,000바이트이며 비교 서버가 응답한 데이터 바이트 × 요청 횟수다. 인덱스 때문에 첫 다운로드는 한국어 약 0.91MB, 영어 약 0.79MB 늘어난다.

로컬 데스크톱의 작은 표본이며 모바일·실제 Pages·p95가 아니다. 특히 영어 주제 검색의 첫 검색 차이는 약 3%로 작아 안정적인 개선이라고 단정하지 않는다. 주된 개선은 사전을 이미 준비한 상태에서의 후보 계산이다.

## 검증과 재현

인덱스 전수 검증은 모든 원본 발음이 해당 구간에 포함되고, 모든 posting이 실제 발음과 일치하는지 양방향으로 확인한다. 한국어 표기 목록도 빠진 행이 없는지 검사한다. 추가 단위 검사는 18,816건의 가중치·복수 발음 후보 비교와 긴 구간 fallback, Unicode 표기 일치를 포함한다.

- 검색 Node 테스트 26개와 프로젝트 검사 통과.
- 기본/주제·빈도 0·5·10의 20조건에서 opt3와 결과 수·전체 점수·순서·표시 메타데이터 일치. `reports/generated/search-index1-parity-weights.json`.
- 교차 언어·전체 언어·미등록 주제·세부 가중치·단어 검색 및 긴 `아름다운`/`beautiful`을 포함한 16개 시나리오가 opt2와 일치. `reports/generated/loading-modes-1790042656563.json`.
- 실제 브라우저의 발음 준비 중 취소/검색어 변경, 계산 중 취소, Worker 오류 후 복구, 최신 요청 우선, 모드 전환 통과. 최종 기록: `reports/generated/linked-worker-smoke-1790042771435.json`.

성능 측정 후에는 인덱스 manifest의 원본 사전·연결 자료·합성어 발음 해시와 로딩 manifest가 서로 같은지도 확인하도록 보호 검사를 추가했다. 행 수가 같아도 다른 버전이면 검색을 중단한다. 검색 루프는 바뀌지 않았으며 이 검사를 포함한 최종 코드에서 단위/UI 검증을 통과했다. 성능 표는 위에 명시한 측정 소스에 대한 기록이다.

```bash
npm run build:boundary-index
npm run validate:boundary-index
npm run benchmark:boundary-index
npm run benchmark:boundary-startup
npm run test:search
npm run check:loading-modes
npm run smoke:linked-ui
```

Node 24를 사용한다. `npm start`가 입력/빌더 변경이나 자산 누락을 발견하면 인덱스를 재생성한다. 별도 정적 서버로 실행할 때는 데이터 압축 빌드와 인덱스 빌드를 먼저 실행한다. 원본 입력 해시와 발음 코드 해시가 manifest에 포함된다.

공개 배포는 하지 않았다. 단어 검색의 주제/빈도 기능 복원, 연결 주제 slider 수식 수정, 전체 평가·모바일 검증과 양쪽 pair 인덱스 확장은 별도 과제로 남는다.
